01 · 设计思路

一个核心：让 AI 与人在「轨迹图」上协作

传统行程规划是「填表 + 看列表」，信息割裂、难以调整。本方案把行程抽象为一张可编辑的轨迹图：节点承载内容与时长，连线承载交通与耗时，人与 AI 都在同一张图上工作。

STEP 1

机票即输入

录入往返航班（或出发/返回日期），系统自动确定目的地、旅行天数与有效游玩时间窗口，无需手动填表。

STEP 2

AI 生成行程

以 POI 数据 + 开放时间 + 交通耗时做约束求解，LLM 润色主题与讲解，输出带时间轴的轨迹图。

编辑闭环，可多轮
STEP 3

轨迹图即画布

删除节点（不去）、加减景点时长、拖动调整顺序、切换交通方式，全部所见即所得，冲突实时提示。

STEP 4

二次 AI 协作

点击「AI 重新规划」，用户编辑固化为硬约束，AI 只优化其余部分，并以差异对比呈现改动。

STEP 5

行程中可调

旅行中按实际情况跳点、加时、重排，后续行程实时重算；天气与营业状态变化自动提醒。

02 · 功能模块

六个模块，覆盖「生成—编辑—再生成—执行」全链路

行程创建

从航班到行程的入口，一次输入完成。

  • 往返航班 / 日期录入，自动算天数
  • 偏好设置：兴趣、节奏、预算、人数
  • 出行模板保存与复用

AI 推荐引擎

多约束求解 + LLM 润色，产出可选的多套方案。

  • POI 检索与评分排序
  • 开放时间 / 交通 / 餐饮时段约束求解
  • 每日主题化讲解与备选方案

轨迹图编辑器

全系统最核心的交互，一切编辑在此完成。

  • 节点删除 / 时长加减 / 顺序拖拽
  • 交通方式切换与耗时更新
  • 时间冲突实时检测、撤销 / 重做

二次 AI 规划

把用户的编辑当约束，AI 重新排布全局。

  • 已编辑节点锁定为硬约束
  • 新旧方案差异对比（增 / 删 / 改）
  • 一键接受或继续微调

旅行中模式

行程不是一次性产物，执行中持续可用。

  • 实时跳点 / 加时 / 重排，后续自动重算
  • 天气、营业状态变化提醒
  • 一键唤起地图导航

行程管理

多段旅程的收纳与分享。

  • 多行程列表、草稿与收藏
  • 生成图片 / 日历导出 / 分享给同行人
  • 节点点赞 / 踩，反哺推荐模型

一条主线，五个阶段

核心闭环：航班输入 → AI 生成 → 轨迹图编辑 → 二次 AI 重排 → 行程中调整。阶段 3 与 4 可反复循环，直到行程满意。

04 · AI 推荐引擎

约束求解为主，LLM 为辅——输出稳定、可解释、可复算

行程推荐不是自由发挥的「生成」，而是带约束的「求解」：任何一次推荐都要满足时间窗口、开放时间与交通可达等硬约束，LLM 负责主题化润色与讲解，确保结果既不冲突、又有「人味」。

约束类型内容示例

用户锁定 二次推荐编辑后节点保留、时长不变、顺序固定、交通方式固定，其余自由优化「洱海待 3h」锁定后其余照常重排

06 · 数据模型

八张表，支撑「行程—节点—边」的图结构

行程的核心数据是图：trips 是画布，itinerary_nodes 是节点（顶点），itinerary_edges 是交通（边），其余为支撑与沉淀表。

表关键字段（示意）职责
usersid, nickname, preferences(JSON)用户与偏好画像
tripsid, user_id, 出发地/目的地, 去程/返程时间, 天数, 状态, ai_version行程主表，一次旅程一张画布
trip_daysid, trip_id, day_no, 日期, 主题按天分组，承载每日主题
itinerary_nodesid, trip_id, day_id, 类型(hotel/attraction/restaurant/transfer), 名称, 开始时间, 占用时长, 顺序, 经纬度, 是否锁定轨迹图顶点：节点与占用时间
itinerary_edgesid, trip_id, from_node, to_node, 方式, 耗时, 备注轨迹图边：交通工具与耗时
poisid, 城市, 类型, 名称, 开放时间, 评分, 价格档, 标签, 经纬度, 来源POI 池：可多源聚合、人工标注

user_feedbackid, node_id, action(赞/踩/跳过), 时间反馈闭环，反哺 POI 评分与推荐权重
07 · 界面设计

移动端竖排轨迹图——「时间即上下，内容即卡片」

示意稿：竖排轨迹图 = 时间流；节点可加 / 减时长、拖拽换序、左滑删除
竖排即时间线

从上到下对应一天的时间流，符合手机阅读习惯；每条交通段标出方式与耗时，机场 / 酒店首尾自然衔接。

编辑一步可达

节点卡片右侧直接 + / − 时长；长按拖拽换序；左滑或按钮删除（确认后节点从图中移除）。

交通可切换

点击交通段弹出方式选择（自驾 / 打车 / 公交 / 地铁 / 步行 / 自行车 / 轮船），系统按路线重算耗时。

冲突实时提示

超出行程窗口、景点闭馆、错过末班车等，节点标红并给出修改建议；支持撤销 / 重做，随时回到上一版。

二次推荐有交代

AI 重排后用颜色标注差异：新增（蓝）、删除（红）、调整（橙），逐条展示理由，接受或继续微调。

10 · 非功能需求

性能、扩展与安全基线（方案目标值）

性能

  • 首屏加载 < 2s（H5 / PWA 缓存）
  • 轨迹图 50+ 节点滚动流畅（虚拟列表）
  • AI 生成秒级返回，重排异步不阻塞

扩展性

  • POI 数据源适配器化，可替换可叠加
  • LLM 厂商适配层，一键切换
  • 行程 JSON 版本化，结构演进不破坏旧数据

安全

  • 全站 HTTPS，接口鉴权与限流
  • 输入校验（防注入），密钥入服务器 .env

体验

  • 触控目标 ≥ 44px，支持 iOS / Android / 微信内置浏览器

11 · 风险与对策

主要风险提前设防

风险影响对策
AI 输出不稳定推荐不可用、格式错乱约束求解为主、LLM 仅润色；输出 JSON Schema 强校验；失败回退规则模板并提示重试
POI 数据质量与更新滞后推荐不准、开放时间过期多源聚合比对；人工标注重点城市；用户反馈（赞 / 踩 / 纠正）闭环修正
移动端复杂交互误触编辑体验差、误删触控区 ≥ 44px；删除需确认；全量撤销 / 重做 + 版本快照可回退
LLM API 依赖厂商故障 / 成本波动适配层多厂商切换；本地规则兜底；用量配额与熔断
地图 / 导航 API 成本预算超支v1 不内置地图视图，导航走系统跳转；v2 按需评估
12 · 待审核决策点

六个关键取舍，请您拍板

以下为影响范围最大的决策，均已给出倾向建议；其余细节待方案通过后细化。

D1用户体系怎么做？
A · 先免登录：单机可用，行程存本地 + 云端匿名；B · 手机号登录：从第一天就建账号体系
建议 A：先跑通核心体验，二期再上登录与多端同步
D2航班数据来源？
A · 手动录入：输入航班号 / 起降时间；B · 接航班 API：自动查询真实班次（成本高）
建议 A：手动录入为主，航班 API 列为可选二期
D3POI 数据源选哪家？
高德 / 百度 / 腾讯地图 POI 接口，均需申请 key 与配额；开放数据（如 OSM）质量不稳定
建议高德 POI：景点覆盖与开放时间字段较好，文档全
D4AI 引擎用什么？
约束求解器 + LLM 润色；LLM 厂商可选豆包 / 通义 / DeepSeek 等
建议：自研求解器保底 + LLM 适配层，首期接任一国内 API
D5平台形态？
A · H5 + PWA：一套代码，免审核，可加桌面图标；B · 小程序：微信生态但受平台约束
建议 A：H5 + PWA 先行，体验与分发成本最均衡
D6是否做地图视图？
A · v1 不做地图：轨迹图已表达时间与顺序；B · 地图联动：点位落图，但涉及 API 成本与开发量
建议 A：v1 专注轨迹图，v2 再评估地图联动
