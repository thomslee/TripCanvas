# 途迹 TripCanvas・旅游行程智能规划系统

依据《旅游行程管理系统需求草稿》开发，方案见 `trip-plan/index.html`。

## 技术栈



* 前端：Vue 3 + TypeScript + Vite + Pinia + Vant（移动端优先）

* 后端：FastAPI + SQLAlchemy 2.0 + Pydantic v2

* 数据库：MySQL 8（本机 root/123456，库 `trip_canvas`）

### M2 改进：真实地点（POI）体系（已完成）

按用户四条意见落地「真实地点」概念：



1. **不改占位节点名**：占位节点显示统称（如「特色餐厅 A」「成都 酒店」），名称由关联的真实 POI 决定；将来选定真实酒店 / 饭店 / 景点后再从高德等渠道细化名称

2. **行程真实地点清单**：置于轨迹图上方（先总览这几天要去的地点再调整），列出行程内全部真实地点（去重 + 出现次数），可在列表选跨天位置「插入」（最前面 / 某节点之后 / 末尾），或直接「移除」→ 轨迹图对应节点级联删除并重建各天边

3. **添加节点两级流程**：搜索真实地点（按行程目的地过滤；内置示例库：大理 / 北京 / 成都 28 条，含营业时间 / 票价 / 评分 / 地址，标「示例」角标；接入高德后将支持全域搜索，适配点 `services/poi_service.py::search_pois`）→ 选位置；或添加占位节点（酒店 / 景点 / 餐厅统称，之后可细化）

4. **暂不拖拽排序**：保留 ↑↓ 换序按钮；占位节点点击 → 同类型真实地点搜索替换；真实节点点击 → 详情弹层（营业 / 票价 / 评分 / 地址）

5. **行程头部信息条**：目的地 + 日期范围 + 天数 + 天气卡（open-meteo 代理，无 Key；失败时显示「天气暂不可用」，见 `services/weather_service.py`）；不再显示总占用时长（每天卡片仍显示当天占用）

6. **天气增强**：天气区独占一行（横向滚动承载多城市卡片），每卡含当天实况 + 穿衣建议（按温度分层 + 雨 / 雪 / 雷 / 雾后缀）+ **未来 5 天预报**（日期 / 图标 / 天气 / 温度区间），10 分钟缓存

7. **清单「添加地点」**：清单头部「＋ 添加地点」→ 搜索真实地点（按目的地）→ 选择位置（跨天：最前面 / 某节点之后 / 末尾），与「插入」同流程；配合「移除」在 AI 推荐后增减感兴趣的地点

8. **操作行独立**：「AI 规划」与「删除行程」置于天气卡下一行

POI 相关 API：`GET/POST /api/pois/search|seed`、`GET/DELETE /api/trips/{id}/pois[/{poi_id}]`；节点增改支持 `poi_id`（关联 / 替换 / 清除）与 `after_node_id`（`-1`= 最前面，`>0`= 某节点之后）；天气：`GET /api/weather?city=大理`（含 `advice` 与 `forecast[]` 5 天）

### M3：AI 二次推荐（智能重排引擎，已完成）



* [x] 确定性重排引擎 `services/replan_service.py`：**不增删**用户节点、保留时长设置，对每天中间节点按「评分降序（占位沉底）+ 类型交替（连续 ≥3 同类型交换）+ 营业时间软约束（开门前节点与下一节点单次交换）」重排，每天首末锚点（通常酒店）不动，重建当天交通边

* [x] `POST /api/trips/{id}/replan`：返回 `{applied, summary, notes, timeline}`，`notes` 为可解释的调整说明（每天最多 4 条，如「营业 11:00 开门，已调整到开门后安排」「评分 4.7，已优先安排」）

* [x] 前端「AI 规划」按钮（操作行）+ 结果说明弹层：展示摘要与每条调整理由；重排后清单与轨迹图联动刷新

* [x] 集成测试 `backend/test_replan.py`：14 项断言（节点集合不变 / 首末锚点不变 / 评分降序 / 边完整 / 幂等 / 营业时间软约束）全绿

* [ ] 将来接入 LLM 后在此结果上做语言润色与个性化说明（当前为确定性引擎，效果可测、无外部依赖）
